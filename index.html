CanonBallCanonBall

The lifecycle agents can run and people can trust.

CanonBall is a method for building and operating software with AI agents. People write down what the system must do. Agents build it and produce the evidence. Every release ships all three together.

See how work movesRead the guide

Why now

Writing software got cheap. Knowing what it does did not.

Agents write faster than people can read.Reviewing every change wastes the agent. Skipping review turns each change into a risk nobody measured.
So the question changed.It used to be "can we build this?". Now it is "what does this change do, and what does the system still promise afterwards?"
The effort moves to verification.Establishing that a promise holds becomes the larger part of the engineering. CanonBall organizes the work around it.

Why the work changed

How work moves

Work moves through seven stations, one milestone at a time.

Related requests are gathered into a milestone. People and agents shape it together, agents build and verify it, an agent reviews it, a person reviews it as well when it is critical, and it is released as a CanonBall. Three practices on the belt, marked 1 to 3, are what make it possible for agents to do most of this work reliably.

Walk it, station by station

What gets written down

People steer agents with a few written things.

Each is a short file in plain language, and most are written at the Shape station. Together they bound what an agent may do: it may take any action consistent with them, and nothing that cannot be traced back to one of them.

People write

Vocabulary

The words the team uses, each defined once.

Delivery: the carrier’s delivered scan for the last item of an order. Not the dispatch.

Why it exists. So that a person, an agent and a check all mean the same thing by the same word.

Learn more about Vocabulary

Tenet

Which good thing wins when two conflict.

A person’s review over speed, when money moves.

Why it exists. An agent facing an undecided choice recommends the way the team would, and says which tenet it used.

Learn more about Tenet

Promise

What the system does for someone.

A customer can request a refund within 30 days of delivery.

Why it exists. It is the reason any code exists. Everything else traces back to one.

Learn more about Promise

Invariant

What must always be true.

A refund is never issued twice for the same order.

Why it exists. It keeps a promise safe to make. After an incident, it is how the fix becomes permanent.

Learn more about Invariant

Decision

A choice that could have gone another way, written down.

A refund is approved automatically while the total refunded on the order stays under $100.

Why it exists. Otherwise an agent decides it for you, and may decide differently next time.

Learn more about Decision

Constraint

What is never allowed, whatever the goal.

No payout above $10,000 without review.

Why it exists. Some lines are not the product team’s to move. A constraint has its own owner, with a veto.

Learn more about Constraint

Assumption

A fact about the outside world the system relies on.

The payment gateway pays at most once per request key.

Why it exists. Evidence holds only while the assumption does, so each one is watched in production.

Learn more about Assumption

Example

One worked case of a clause: given, when, then.

Given order 4471 and a refund request with request key K, when the same request, with request key K, is sent a second time and both are reviewed, then one payout is made for order 4471.

Why it exists. Plain sentences hide decisions. People approve examples, and each check is written from one.

Learn more about Example

Five of these are clauses

A promise, an invariant, a decision, a constraint and an assumption are each a kind of clause: one file with an ID and its examples.

The approved clauses together are the canon.

people approvespec/canon/vocabulary.md

Vocabulary

Each noun is defined once. Synonyms are not allowed, and a clause that uses an undefined word is blocked. Agents read this file before anything else, so the same words run from the promise to the code, the check and the incident report.

It grows whenever an open question about a word is answered.

## Order
One purchase by a customer: one or more items, paid for together.

## Dispatch
The carrier's collection of the last item of an order.

## Delivery
The carrier's delivered scan for the last item of an order. Not the dispatch.

## Refund
Money returned to the customer for an order. Each refund is separate; an order can have more than one.

## Refund amount
The money returned by one refund. Not the order total.

people approvespec/canon/INV-004-no-double-payout.md

An invariant

What must always be true. People approve its worked examples, and the examples fix the meaning: here, that "twice" means the same request paid two times. A second, separate refund on an order is a new refund.

---
id: INV-004
kind: invariant
title: No double payout
traces: [REQ-012]
terms: [refund, order]
owner: refunds owner
tier: 2
---
A refund is never issued twice for the same order.

"Twice" means the same request paid two times: a request sent again, retried, or delivered in two copies.
A second, separate refund on the same order is a new refund, with its own request key, and is allowed.

## Examples

### satisfies/1: The same request sent twice pays once
Given order 4471 and a refund request with request key K
When the same request, with request key K, is sent a second time and both are reviewed
Then one payout is made for order 4471

### satisfies/2: A retry after a lost reply finds the original payout
Given a reviewed refund whose payout reaches the payment gateway, which pays it, and whose reply is lost
When the service retries the payout
Then the retry finds the original payout and nothing more is paid

### violates/1: Two concurrent copies of one request both pay out
Given two copies of one refund request, with the same request key, arriving at the same time
When both copies are processed and reviewed
Then two payouts are made for the order

A decision

A choice that could have gone another way, written down. This one is proposed by the change in roadmap/. It becomes canon only when that change is released.

Follow the change to watch it arrive.

---
id: DEC-031
kind: decision
title: Auto-approve under $100
traces: [REQ-012]
cites: [tenet 1]
terms: [refund, refund amount, order, review]
owner: product manager
tier: 2
---
A refund is approved automatically while the total refunded on the order stays under $100.

The limit applies to the total refunded on the order, this refund included, and not to each refund amount on
its own, so that a refund split into small pieces still goes to review. Settled by tenet 1: a person's review
over speed, when money moves. Every other refund inside the window goes to review, as before.

## Examples

### satisfies/1: A $40 refund, nothing refunded before
Given an order on which nothing has been refunded
When the customer requests a refund of $40
Then the refund is approved without review

### satisfies/2: Two $60 refunds on one order
Given an order on which a refund of $60 has already been paid
When the customer requests a second refund of $60
Then the second refund goes to review

### violates/1: A $250 refund approved without review
Given an order on which nothing has been refunded
When the customer requests a refund of $250
Then the refund is approved without review

planner agentspec/blueprint/cases/INV-004.md

The case for one clause

It splits the clause into parts, names the environment that checks each part, and argues why the parts are enough. Cases about money and safety are reviewed by a person. This is the argument of the case for INV-004.

## Argument

A refund is paid twice only if the gateway transfers money twice for one request. The service sends every
payout for a request under that request's key (P1), and the gateway transfers at most once per key (P2). So
for the same request, at most one transfer happens. P1 covers everything the service controls, on both paths;
P2 is the one thing it does not, which is why it is an assumption with a monitor rather than a check.

The automatic path adds no new way to reach the gateway: it calls the same `pay`, whose retry and request-key
handling DEC-031 does not change. The check on the automatic path shows this rather than assumes it.

VE-002 cannot show whether the real gateway honors request keys. That is the residual risk, and it is the
risk the monitor watches.

Verification engineering

This is where most of the engineering now goes. Writing the change is the small part. The work is building a place where a clause can be shown to hold, and shown to fail when it should. The builder can run everything here and change none of it.

Making an environment stricter is free. Making it weaker is reviewed.

# verify

Written by the verifier agent. The builder may run everything here and may change none of it.

- `envs/` the verification environments: the system, its real local stores, and a fake for each outside dependency.
- `checks/` one check per example, marked with the example it encodes (`verify/canonball_check.py`).
- `checks/red/` the kept failing runs that show each check can fail. Written by `tools/canonball fault`.
- `faults/` injected faults: small patches that break one thing on purpose.

One check per example

Each check names the example it encodes. An example with no check is visible, and so is a check with no example. This one is in test_inv004_no_double_payout.py.

    @example_of("INV-004#violates/1", "Two concurrent copies of one request both pay out")
    def test_two_concurrent_copies_pay_once(self):
        world = self.world
        order = world.rig.order(total_cents=12000)

        def one_copy():
            refund = world.act.request_refund(order, 12000, key="concurrent-1")
            return world.act.approve(refund.id, reviewer="support lead")

        at_once(one_copy, one_copy)
        paid = world.observe.gateway.payouts(order=order)
        assert len(paid) == 1

Verification engineering

Verification engineering takes the larger share of the effort.

When agents write the code, producing a change is quick and establishing that it is correct is the harder problem. The environments in which promises are checked therefore deserve the same design attention as the product. They are designed with a person who understands them, because evidence is only as credible as the method that produced it.

A verification environment has seven parts

  • BoundaryWhat is under test: the refunds service, at this commit.
  • StimulusHow it is driven: requests through the public interface.
  • WorldWhat surrounds it: a real local store, a fake payment gateway.
  • ProbesWhat can be observed: what the store holds, what the gateway paid.
  • OracleWhat decides pass or fail: a mechanical check, not an opinion.
  • CoverageWhat was exercised, and which injected faults were caught.
  • ControlSeed, clock, a clean start and a clean teardown.
It also states what it cannot show. Real gateway timing, for one. Evidence counts only inside what the environment can show.

A check must fail once before its pass counts

test_same_request_twice_pays_oncepassed, seen to fail
test_retry_after_lost_reply_pays_oncepassed, seen to fail
test_retry_after_lost_reply_on_automatic_path_pays_oncepassed, seen to fail
test_two_concurrent_copies_pay_oncepassed, never seen to fail

Observability

Observability gives agents the context people used to carry.

An experienced engineer debugs with years of knowledge about how the system behaves. An agent begins each task with none of that knowledge, so it depends on what the system can tell it. When every decision is logged with its reason and every request can be traced, an agent can diagnose a fault from the evidence instead of speculating about the code.

Three rules

  • DecisionsEvery decision the system makes is logged with the clause it applied and the inputs it used.
  • TracesOne trace follows each request through every adapter.
  • ToolsAgents have commands to read logs, traces, metrics and state, and to replay a request.
The same tools serve three stations. The builder uses them to see what its code does, the verifier to explain why a check failed, and the on-call agent to diagnose an incident. People read the same signals, so they can check what an agent concluded.

A recommended architecture

Keep decisions apart from side effects.

Agents do their best work inside clear structure. CanonBall does not dictate how your code is laid out. It recommends one habit, because it makes evidence cheap: put the logic that decides in one place, and the code that touches the outside world in another.

Inputs come in as dataThe request, the current time, a reading from a sensor. The logic never fetches them itself.
→
Decision logic: the functional coreGiven this state and this input, what should happen? No database, no network, no clock. The same inputs always give the same answer.
checked for every input
→
Adapters: the imperative shellPaying out, sending an email, writing a row. Each goes through one named place.
people still review this code
You may already know it.Gary Bernhardt named it functional core, imperative shell. Alistair Cockburn's ports and adapters is the same idea.
Why it suits agents.Logic with no side effects can be tested exhaustively, replayed exactly, and rewritten safely.
What people keep.The interface, the constraints, the adapters, and any design choice they promote to a decision.

An architecture agents can work in

Adoption

Hand over decisions as agents earn them.

Each kind of decision has its own level of automation, so a team can keep architecture or detailed design with a person for as long as it wants and hand over other decisions sooner. A team starts with agents recommending and people deciding, and moves each setting on track record. Review works differently: an agent reviews every change at every setting, and a person reviews as well whenever the policy lists the change as critical.

Start

Begin from a repository that is already laid out.

The starter repository has the folders, templates and policy pages described here, an AGENTS.md that teaches an agent the method, and tools/canonball, a small program that checks the canon, records evidence, computes the Verification Record and performs releases. Fork it, fill in the top of AGENTS.md, and point your agent at it.

Start a repository

git clone https://github.com/sheshavpd/CanonBall my-system
cd my-system
tools/canonball check
tools/canonball new milestone M1-first-promise

Python 3.11 is the only requirement of the tooling. The system itself can be written in any language.
