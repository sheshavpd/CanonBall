# Signals

What the refunds service emits, so that agents and people can see what it did. Agents and monitors depend on
these names, so a change to this page is reviewed like a change to an interface. Never log personal data; log
identifiers and amounts.

## Decision log

Every call to `decide_refund` writes one JSON line to the decision log (`src/refunds/adapters/decision_log.py`).
In production the path is `$REFUNDS_DECISION_LOG`; in VE-002 each world has its own file.

| Field | Meaning |
|---|---|
| `order` | The order id. |
| `clause` | The clause the decision applied, e.g. `REQ-012`. |
| `result` | `in_review` or `refused`. |
| `reason` | Why, in a few words, e.g. `day 31 of 30`. |
| `inputs` | Everything the decision used, below. Enough to replay it. |
| `trace` | The trace id of the request that asked for the decision. |
| `at` | When it was written, UTC, ISO 8601. |

`inputs`:

| Field | Meaning |
|---|---|
| `order_total_cents` | The order's total. |
| `dispatched_on` | The day of dispatch, ISO date. |
| `delivered_on` | The day of delivery, ISO date. |
| `amount_cents` | The refund amount requested. |
| `refunded_cents` | What had already been refunded on the order, as the service read it. |
| `today` | The day of the request, ISO date. |
| `counted_from` | Which day of the order the refund window was counted from: `dispatch` or `delivery`. |
| `window_start` | That day, ISO date. |

## Traces

One trace id per refund request, generated by the service and written with its decision.

## Metrics

The monitor in `verify/monitors/duplicate-payouts.md` reads payouts per request key from the payment gateway's
settlement report, and payouts per refund from the store.

## Tools

`observe/tools/observe decisions --order N` prints the decisions for an order; `observe/tools/observe replay
--order N` re-runs them with the current code. Both are read-only.
