# Assurance case: INV-004

INV-004: a refund is never issued twice for the same order. "Twice" means the same request paid two times.

A refund reaches the gateway by one of two paths: the review path (`approve`, after a person's review) and,
from DEC-031, the automatic path (`request_refund`, for a refund approved automatically). Both pay through
the same `pay`, under the refund's request key. The parts below hold for both paths.

## Parts

| Part | Claim | How it is supported |
|---|---|---|
| P1 | A repeated request never pays again: a request sent twice, retried after a lost reply, or arriving in two concurrent copies leads to one payout attempt sequence under one request key, on either path. | Checked in VE-002: INV-004 satisfies/1, satisfies/2 and violates/1, each seen to fail against an injected fault. On the automatic path, a check runs an automatically approved refund against the lost-reply failure. |
| P2 | The gateway pays once per request key. | Assumed: ASM-011. Watched in production by `verify/monitors/duplicate-payouts.md`. VE-002's fake gateway behaves as ASM-011 says. |

## Argument

A refund is paid twice only if the gateway transfers money twice for one request. The service sends every
payout for a request under that request's key (P1), and the gateway transfers at most once per key (P2). So
for the same request, at most one transfer happens. P1 covers everything the service controls, on both paths;
P2 is the one thing it does not, which is why it is an assumption with a monitor rather than a check.

The automatic path adds no new way to reach the gateway: it calls the same `pay`, whose retry and request-key
handling DEC-031 does not change. The check on the automatic path shows this rather than assumes it.

VE-002 cannot show whether the real gateway honors request keys. That is the residual risk, and it is the
risk the monitor watches.
