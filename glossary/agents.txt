# CanonBall glossary

> Every term the guide uses. Where the specification uses a different word, it is shown in brackets.

- Site: CanonBall. The lifecycle agents can run and people can trust.
- HTML page: https://canonball.org/glossary/
- This file: https://canonball.org/glossary/agents.txt

---

Adapter [door]
  The code through which one kind of side effect reaches the outside world, such as a payout or an email. Together the adapters form the imperative shell.
  Explained in: https://canonball.org/guide/architecture/agents.txt

Agent review
  The review every milestone and every piece of unplanned work gets from the reviewer agent, whether or not a person reviews as well.
  Explained in: https://canonball.org/guide/review/agents.txt

AGENTS.md
  The first file an agent reads in a repository. Its top part is specific to the repository; its appendix summarizes CanonBall.
  Explained in: https://canonball.org/guide/agents-md/agents.txt

Agreement gate [Gate 1]
  The end of the Shape station: a person agrees to a change proposal and approves its examples. Always required when a change adds or alters a clause.
  Explained in: https://canonball.org/guide/shape/agents.txt

Assembly
  The one file that says which unit fills each role.
  Explained in: https://canonball.org/guide/composition/agents.txt

Assumption
  A fact about the outside world a clause relies on, with a plan for watching it and for what happens when it fails.
  Explained in: https://canonball.org/guide/primitives/agents.txt

Assurance case [case]
  For one clause: the parts it splits into, the environment that checks each part, and the argument that the parts are enough. The term comes from safety engineering.
  Explained in: https://canonball.org/guide/verification-engineering/agents.txt

Assurance policy
  Rules, owned by people, that turn evidence into a status and say when a person must accept a release. No agent may write them.
  Explained in: https://canonball.org/guide/evidence/agents.txt

Back pressure
  The upkeep a running system demands: incidents, bugs and reliability problems that come back as work.
  Explained in: https://canonball.org/guide/workflow/agents.txt

Blast radius
  How much can break if a change is wrong: which clauses, which customers, and whether it can be undone.
  Explained in: https://canonball.org/guide/review/agents.txt

Blueprint
  The agents’ design for keeping the canon: architecture, one assurance case per clause, and the verification plan.
  Explained in: https://canonball.org/guide/layers/agents.txt

Builder
  The agent that writes the code. It can run the checks and cannot change them.
  Explained in: https://canonball.org/guide/people-and-agents/agents.txt

Canon
  The set of clauses people have approved. It describes what the system promises today.
  Explained in: https://canonball.org/guide/layers/agents.txt

CanonBall
  The method. Also one release of a system: the canon, the build and the Verification Record, fixed together.
  Explained in: https://canonball.org/guide/canonball/agents.txt

Change proposal [change.md]
  One page that answers "what changes in the system?", with the clauses it adds and why now.
  Explained in: https://canonball.org/guide/collect/agents.txt

Check
  An automated test that encodes one example and decides pass or fail from what it observes.
  Explained in: https://canonball.org/guide/evidence/agents.txt

Clause
  One statement in the canon: a file with an ID, a kind and its examples. Promises, invariants, decisions, constraints and assumptions are all clauses.
  Explained in: https://canonball.org/guide/primitives/agents.txt

Constraint [envelope]
  What is never allowed, whatever the goal. It has its own owner, with a veto. Safety engineering calls these safety constraints.
  Explained in: https://canonball.org/guide/primitives/agents.txt

Content hash [digest]
  A short value computed from the contents of some files. When the files change, the hash changes, and evidence that relied on them is stale.
  Explained in: https://canonball.org/guide/evidence/agents.txt

Contract tests [conformance suite]
  The tests any provider of a role must pass.
  Explained in: https://canonball.org/guide/composition/agents.txt

Decision
  A choice that could have gone another way, written down so it is not silently made again.
  Explained in: https://canonball.org/guide/primitives/agents.txt

Decision log
  A record the running system writes for each decision: the clause it applied, the inputs it used and the result.
  Explained in: https://canonball.org/guide/observability/agents.txt

Decision logic [pure core]
  Code that decides what should happen from explicit inputs, with no side effects. Also called the functional core.
  Explained in: https://canonball.org/guide/architecture/agents.txt

Elicitor
  The agent that drafts clauses and change proposals from conversations, and files questions when something is ambiguous.
  Explained in: https://canonball.org/guide/people-and-agents/agents.txt

Escaped defect [escape]
  A problem that passed every gate and reached production.
  Explained in: https://canonball.org/guide/environments/agents.txt

Evidence
  The recorded result of one check run: what was checked, against which code, in which environment, with what outcome.
  Explained in: https://canonball.org/guide/evidence/agents.txt

Example [story]
  One worked case of a clause, written as given, when, then. Examples are what people approve. Behavior-driven development calls it a scenario.
  Explained in: https://canonball.org/guide/examples/agents.txt

Express belt
  The path for unplanned work: repairs and upkeep that change no promise. It skips the batching into a milestone and none of the stations.
  Explained in: https://canonball.org/guide/collect/agents.txt

Fake
  A working stand-in for an outside dependency, such as a payment gateway that runs in memory. One kind of test double.
  Explained in: https://canonball.org/guide/environments/agents.txt

Forward pressure
  People pushing new requests into the system.
  Explained in: https://canonball.org/guide/workflow/agents.txt

Held-out scenarios [holdout]
  Scenarios that people write and keep where neither the builder nor the verifier can read them.
  Explained in: https://canonball.org/guide/environments/agents.txt

Holdout keeper
  The agent that runs the held-out scenarios, which people write, and reports only pass or fail.
  Explained in: https://canonball.org/guide/people-and-agents/agents.txt

Incident
  A failure in production. It is diagnosed, repaired on the express belt, and leaves an example behind.
  Explained in: https://canonball.org/guide/operate/agents.txt

Injected fault [seeded fault]
  A small deliberate defect, applied to a scratch copy, used to show that a check can fail. Mutation testing calls it a mutant.
  Explained in: https://canonball.org/guide/evidence/agents.txt

Invariant
  What must always be true for the system to be correct.
  Explained in: https://canonball.org/guide/primitives/agents.txt

Level of automation [autonomy level]
  How far one kind of decision has been handed to agents, from "agent analyzes" to "agent acts, people watch the metrics".
  Explained in: https://canonball.org/guide/delegation/agents.txt

Milestone
  A batch of related requests shaped and built together: one change proposal, the files it proposes, and the tasks to build it. The unit in which work moves.
  Explained in: https://canonball.org/guide/collect/agents.txt

Monitor
  A check that runs in production and watches an assumption or an invariant. When it fires, an incident opens.
  Explained in: https://canonball.org/guide/operate/agents.txt

Observability
  How much of a system’s inner state can be read from outside it. Here, the signals a system emits and the tools agents use to read them.
  Explained in: https://canonball.org/guide/observability/agents.txt

On-call agent
  The agent that watches the monitors, diagnoses incidents with the observability tools, and drafts the repair. A person decides anything risky.
  Explained in: https://canonball.org/guide/operate/agents.txt

Oracle
  Whatever decides whether an observed result is correct. A mechanical check is the preferred kind.
  Explained in: https://canonball.org/guide/environments/agents.txt

Orchestrator
  A program, not an agent. It computes the state of every milestone and task from what exists in the repository, compares predicted with actual behavior, and performs the release.
  Explained in: https://canonball.org/guide/people-and-agents/agents.txt

Planner
  The agent that writes the blueprint: the design, the assurance cases, and the predicted change in behavior.
  Explained in: https://canonball.org/guide/people-and-agents/agents.txt

Predicted change in behavior
  A statement, written at Shape, of how the system’s behavior will differ after a milestone. At Review it is compared with what actually changed.
  Explained in: https://canonball.org/guide/shape/agents.txt

Promise [requirement]
  What the system does for someone.
  Explained in: https://canonball.org/guide/primitives/agents.txt

Recorded failure [red proof]
  The kept output of a run in which a check failed against an injected fault. It shows the check can fail.
  Explained in: https://canonball.org/guide/evidence/agents.txt

Release
  The only event that changes spec/. It copies in a change’s proposed files and publishes a CanonBall.
  Explained in: https://canonball.org/guide/release/agents.txt

Release candidate [candidate present]
  spec/ with one change’s proposed files applied. Checks for that change run against it.
  Explained in: https://canonball.org/guide/release/agents.txt

Release gate [Gate 2]
  At the Review station, a person accepts the remaining risk of a release. Required only when the policy says the change is critical.
  Explained in: https://canonball.org/guide/review/agents.txt

Release rule
  A milestone may be released when every clause it touches is accepted and no other clause got worse.
  Explained in: https://canonball.org/guide/release/agents.txt

Request
  Anything someone asks of the system before it has been shaped: a complaint, a number, an idea. Related requests gather into a milestone.
  Explained in: https://canonball.org/guide/collect/agents.txt

Reviewer
  The agent that reviews every change against its clauses and the Verification Record. It writes nothing but its review.
  Explained in: https://canonball.org/guide/review/agents.txt

Role
  A contract one unit defines for something it needs another to provide, published with contract tests and a fake.
  Explained in: https://canonball.org/guide/composition/agents.txt

Station
  One of the seven stops a milestone passes: Collect, Shape, Build, Verify, Review, Release, Operate.
  Explained in: https://canonball.org/guide/workflow/agents.txt

System under test [boundary]
  The part of the system a verification environment exercises.
  Explained in: https://canonball.org/guide/environments/agents.txt

Tenet
  A statement of which good thing wins when two conflict, written as X over Y. Agents cite tenets when they recommend. Not a clause.
  Explained in: https://canonball.org/guide/tenets/agents.txt

Tier
  How critical a clause is, from 0 to 2. It sets how much argument its assurance case needs and whether a person reviews it.
  Explained in: https://canonball.org/guide/verification-engineering/agents.txt

Trace
  The record of one request’s path through the system, under one ID.
  Explained in: https://canonball.org/guide/observability/agents.txt

Unit
  A separately owned part of a system with its own canon, build and Verification Record. A service, a subdomain and a domain are all units.
  Explained in: https://canonball.org/guide/composition/agents.txt

Unplanned work
  An incident repair, a bug fix, a refactoring or other upkeep: work that restores a promise or changes none. It has a small change proposal, rides the express belt, and is released on its own.
  Explained in: https://canonball.org/guide/collect/agents.txt

Verification engineering
  The work of building environments and checks that can show a clause holds, and can show it failing.
  Explained in: https://canonball.org/guide/verification-engineering/agents.txt

Verification environment
  A designed place to produce evidence, with seven parts and a statement of what it cannot show.
  Explained in: https://canonball.org/guide/environments/agents.txt

Verification level
  What a part of a clause depends on, from pure logic (0) to physics and people (4). It decides the method.
  Explained in: https://canonball.org/guide/verification-engineering/agents.txt

Verification Record [Record]
  The status of every clause, computed from evidence. It is published, and nobody edits it. The guide shortens it to "the Record" after first use.
  Explained in: https://canonball.org/guide/evidence/agents.txt

Verifier
  The agent that builds environments, checks and monitors. It cannot change the code it judges.
  Explained in: https://canonball.org/guide/people-and-agents/agents.txt

Vocabulary [glossary]
  The file that defines each noun the team uses, once. Domain-driven design calls the result a ubiquitous language.
  Explained in: https://canonball.org/guide/vocabulary/agents.txt
