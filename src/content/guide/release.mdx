## What arrives

A reviewed milestone. At this station no person decides anything and no agent does. The orchestrator applies a rule.

## The release rule

Checks for a milestone run against the **release candidate**: `spec/` with the milestone's proposed files applied. The milestone may be released when two things are true of the Verification Record computed for that candidate.

1. Every clause the milestone touches is accepted.
2. No clause it did not touch has become worse, unless a named person accepted that at the release gate.

The second condition protects everything already promised. A milestone carries no list of things it must not break, because the Record checks every clause every time.

## What the orchestrator does

When the rule holds and the review has passed, the orchestrator:

1. copies the files in `diff/` over the files of the same name in `spec/`;
2. archives the milestone folder;
3. publishes a CanonBall;
4. hands the build that CanonBall names to the team's deployment pipeline.

If another milestone was released in the meantime, the candidate is rebuilt on the new `spec/` and the checks run again before anything is copied.

No person edits `spec/` by hand. That is what lets `spec/` describe the system as released, with evidence, and not as someone hoped it would be.

How the build is rolled out and rolled back is the pipeline's job. CanonBall says which build goes out and what it promises.

## What a CanonBall holds

```text
CanonBall 13
  canon    spec/canon at this release
  build    commit 3f9c
  record   4 accepted, 1 accepted with stated risk,
           0 unsupported
  notes    + DEC-031 A refund is approved automatically while the
             total refunded on the order stays under $100
```

Three things are fixed together at one moment: what the system promises, the code that keeps the promises, and the evidence that it does. Together they answer "what does this system promise, and how do you know?" without anyone reading code. [What a CanonBall is](../canonball/) goes further.

The one clause "accepted with stated risk" is ASM-011, the assumption about the payment gateway. It cannot be proven from here, so it is watched in production.

## When the rule does not hold

The milestone stays on the belt. The Record names the clause that is holding it and the part of that clause with no evidence, so the work goes back to a specific place.

| What the Record shows | Where the milestone goes |
|---|---|
| A touched clause is unsupported | [Verify](../verify/), for the missing evidence |
| A check fails | [Build](../build/) |
| An untouched clause got worse | [Build](../build/), or [Review](../review/) if someone means to accept it |

Whether the milestone is done is not a matter of opinion. The status is computed.

## What leaves

`spec/` now describes a system in which small refunds are approved automatically, and that system is running as CanonBall 13. It is [operated](../operate/) from here.
