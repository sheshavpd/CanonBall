## What arrives

CanonBall 13, running. Two things watch it.

**Monitors** watch the assumptions the evidence rested on. The refunds service assumes the payment gateway pays at most once per request. Nothing in a test can prove that about someone else's system, so it is watched in production instead.

The **on-call agent** watches the monitors, the error rates and the support queue.

## Back pressure

A running system asks for upkeep. Customers find cases nobody wrote an example for. Dependencies change. Load grows. This is **back pressure**: work that arrives from the system itself, on its own schedule.

In many teams this work lives in a separate process with separate people. Here it rides the same belt, because a repair that skips verification is how the next incident is made.

## A refusal on day 29

Three weeks after the release, a customer writes to support. Their refund was refused as too late. They are sure they asked within 30 days.

The on-call agent opens incident INC-031. It does not guess, and it does not read the code first. It asks the system what it decided for that order.

```text
$ observe decisions --order 5512

REQ-012  refund window
  result        refused
  reason        day 31 of 30
  counted from  dispatch, 2 March
  delivered     4 March
```

The cause is on the screen. The window was counted from the day the order was dispatched. The vocabulary says **delivery** means the carrier's delivered scan. One part of the code read the wrong date.

Diagnosis took minutes because the decision log exists. Without it, the agent would have had a refused refund, a date, and a long list of things that might be wrong.

## The person's part

Two things here are not the agent's to do.

Paying this customer now is money moving outside the normal path. The **operator** approves it.

The repair changes who gets a refund, so its example needs a person's agreement like any other.

## The repair takes the express belt

The fix restores what was already promised, so it does not wait for a milestone. It gets a small folder under `roadmap/unplanned/` and passes the same stations.

| Station | What happens |
|---|---|
| Shape | The failing case becomes an example. A new invariant is proposed: INV-009, the refund window is counted from delivery, never from dispatch. The product manager approves both. |
| Build | The builder corrects the date. |
| Verify | The verifier writes the check, sees it fail against the old code, and adds a late-delivery case to VE-002. |
| Review | The reviewer agent reviews it. It concerns who is paid, so the owner looks too. |
| Release | CanonBall 14. |

## What the system keeps

The incident is filed in `incidents/` and stays there.

```text
INC-031  Refund refused on day 29.
         The delivery date was read from dispatch.

Example added:   delivered 3 March, requested 1 April: accepted
Proposed:        INV-009
```

Two things are now permanently better. The canon has an invariant it lacked, with a check that has been seen to fail. And the verification environment covers a case it missed.

After every problem that reaches production, the team asks one more question: why did the environment not catch this? The answer goes into the environment. That is how back pressure is turned into a system that needs less of it.
