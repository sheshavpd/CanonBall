## What arrives

CanonBall 13, running.

**Monitors** watch the assumptions the evidence rested on. The refunds service assumes the payment gateway pays at most once per request key (ASM-011). No test can prove that about someone else's system, so a monitor watches for it in production.

The **on-call agent** watches the monitors, the error rates and the support queue.

## Back pressure

A running system asks for upkeep. Customers find cases nobody wrote an example for, dependencies change, and load grows. This is **back pressure**: work that arrives from the system itself, on its own schedule.

In many teams this work has its own process and its own people. Here it rides the same belt, because a repair that skips verification is how the next incident is made.

## A refusal on day 29

Three weeks after the release, a customer writes to support. Their refund was refused as too late, and they are sure they asked within 30 days.

The on-call agent opens incident INC-007 and asks the system what it decided for that order.

```text
$ observe decisions --order 5512

REQ-012  refund window
  result        refused
  reason        day 31 of 30
  counted from  dispatch, 2 March
  delivered     4 March
```

The window was counted from the day the order was dispatched. The vocabulary says **delivery** means the carrier's delivered scan, so one part of the code read the wrong date.

The cause was read from the decision log. Without the log, the agent would have had a refused refund, a date, and a long list of things that might be wrong.

One more fact belongs in the incident. REQ-012 showed as accepted the whole time. Its checks passed, because none of them used an order whose dispatch and delivery dates differed. Accepted means supported by the evidence so far, and the evidence had a gap.

## The person's part

Paying this customer now is money moving outside the normal path, so the **operator** approves it.

The repair adds an example and an invariant, and both need a person's approval like any other.

## The repair takes the express belt

The fix restores what was already promised, so it does not wait for a milestone. It gets a small folder under `roadmap/unplanned/` and passes the same stations.

| Station | What happens |
|---|---|
| Shape | The failing case becomes an example. An invariant is proposed to pin down what REQ-012 already says: INV-009, the refund window is counted from delivery, never from dispatch. The product manager approves both. |
| Build | The builder corrects the date. |
| Verify | The verifier adds late delivery to the starting states VE-002 can set up, writes the check, and sees it fail against the old code. |
| Review | The reviewer agent reviews it. It decides who is paid, so the refunds owner looks too. |
| Release | CanonBall 14. |

## What the system keeps

The incident is filed in `incidents/` and stays there.

```text
INC-007  Refund refused on day 29.
         The delivery date was read from dispatch.

Example added:   dispatched 2 March, delivered 4 March,
                 requested 2 April: accepted
Proposed:        INV-009
```

The canon now has an invariant with a check that has been seen to fail, and the verification environment covers a case it missed.

After every problem that reaches production, the team asks why the environment did not catch it, and the answer goes into the environment. Over time this is what reduces back pressure.
