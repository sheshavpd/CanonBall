## What an environment is

A **verification environment** is a place built to produce evidence about a clause. You may know a simpler relative as a test harness. An environment differs in three ways: it has a declared boundary, it states what it cannot show, and its own reliability is measured.

## Seven parts

Every environment, at every level, has the same seven parts. Hardware verification settled on them decades ago.

<Figure id="environment" />

One part needs a note. The **probes** are not special test code. They are the system's [observability](../observability/) tools pointed at the test world: the commands that read logs, traces, metrics and state in production read the same things here. A check sees the system through them, and when a check fails, the verifier agent uses them to explain why.

## It states what it cannot show

Each environment is declared in a short file. The most important section is the last one.

```markdown
id: VE-002
name: payments-sandbox
level: 2
boundary: the refunds service, at this commit
world: real local store; a fake payment gateway
control: seeded; one command up, one command down

## What it cannot show
Real gateway timing. Whether the real gateway honors
request keys. Database contention. Production request shapes.
```

Evidence counts only inside what the environment can show. A check that passes here says nothing about real gateway timing, and the Verification Record will not pretend otherwise.

Write this section first, before any code. It lists the claims this environment must decline to support.

## Four verbs

An environment exposes a small, fixed set of actions. Checks, held-out scenarios and exploring agents all drive it through the same ones.

| Verb | Does |
|---|---|
| `rig` | Sets up the starting state |
| `act` | Drives the system through a real channel |
| `perturb` | Makes something misbehave: a timeout, a lost reply, a refusal |
| `observe` | Reads what actually happened, from an authoritative place |

Two more, `up` and `down`, create and destroy the whole thing.

```python
def test_retry_after_lost_reply_pays_once(world):
    order = world.rig.order(amount_cents=1999).result
    assert world.perturb.gateway.lose_reply("payout", times=1).ok
    world.act.api.refund(order)          # the payout happens; the reply is lost
    world.act.api.refund(order)          # the client retries
    paid = world.observe.gateway.payouts(order=order).result
    assert len(paid) == 1
```

Two rules about these verbs prevent most self-deception.

> **The environment never judges.** It drives and it observes. Deciding pass or fail is the check's job. A helper that returns "passed" has quietly become its own oracle.

> **Observe the authoritative place.** Read the database, or the fake's log of what it executed. Never read the test driver's belief about what it did.

## Three kinds of fidelity

An environment can be unrealistic in three separate ways.

| Fidelity | The question |
|---|---|
| **World** | How real are the surroundings? |
| **Actor** | Do the simulated users behave like real ones? |
| **Oracle** | Does "passed" actually mean correct? |

They fail independently, and the oracle is usually the weakest. Oracles are therefore preferred in a fixed order: a mechanical check first, then comparison against a reference model, then a model used as a judge with its noise measured, and human review last.

## Rules that keep an environment trustworthy

| Rule | What it means |
|---|---|
| **Evidence counts only within the validated range** | If a simulator was validated for speeds up to 2 m/s, a scenario at 3 m/s is out of range. It does not count, even if it passes. |
| **An environment that never fails proves nothing** | Every environment must catch injected faults it was not tuned on. Those faults are held where the verifier cannot read them. If the share it catches falls, the evidence it produced is discounted. |
| **Fakes pass the real thing's tests** | A fake payment gateway runs the same contract tests as the real one. A fake that drifts from the real behavior fails its own test. |
| **Stricter is free, weaker is reviewed** | Adding scenarios or tightening a check needs nobody's permission. Removing a scenario, loosening a threshold, or swapping the oracle is reviewed by a person. |

The last rule exists because one quiet edit to a shared environment could weaken all the evidence it ever produced.

## Races and timing

Some clauses are about what happens when two things overlap. To check one, the environment must be able to hold the gap open on purpose.

A **window** is the interval between two effects where an interruption changes the outcome. The gap between the gateway paying out and its reply arriving is one. Each environment says, for each window, whether it can hold it open, whether it is atomic here, or whether it is left to real timing.

A check about a race that never actually opened the window proves nothing, and is recorded that way.

## Designing one

An environment is designed before it is built, and a person is part of the design.

### Who designs it

The verification lead and the verifier agent design it together. Which of them leads is [the team's choice](../delegation/). One condition holds in every team.

> **A person can always explain how each clause is checked.** If nobody can, the design is not finished, however many checks pass.

### What they decide

The design answers three questions. Here they are for VE-002.

| Question | For the payments sandbox |
|---|---|
| **Which failures must the system survive under test?** | A lost reply. A refusal. The gateway pays and then times out. Each becomes a `perturb` action. |
| **What is faked, and how faithfully?** | The payment gateway is a fake that passes the real gateway's contract tests. The store is real and local. |
| **What can the environment not show?** | Real gateway timing, database contention, production request shapes. |

A failure left off the first list is never tried. A fake described too generously supports claims it should not. The lead reads all three answers before any check is written.

### The order of work

1. Collect the parts of assurance cases that need this boundary at this level.
2. Write the declaration, starting with what the environment cannot show.
3. List the failures and build the fakes. Pin each fake to the real thing's contract tests.
4. Make the environment start and stop with one command each, and expose the verbs.
5. Inject faults and measure what gets caught.

The chapter on [starting](../start/) walks through a first one.

### It is kept like product code

| Like product code, it is | For an environment |
|---|---|
| **Reviewed** | The verification lead reads the declaration. Any change that weakens the environment is reviewed by a person, under the rule above. |
| **Versioned** | The declaration lives in `spec/blueprint/environments/` and the code in `verify/envs/`. A change to either makes the evidence it produced [stale](../evidence/#how-staleness-works). |
| **Improved after every escaped defect** | An **escaped defect** is one that reached production past every check. Each one asks why the environment did not catch it. |

The answer to that question is a new starting state, a new `perturb` action, or a new line under "What it cannot show".

Take a customer refused a refund on day 29, because the 30-day window was counted from dispatch. The repair adds an example, and the example needs an order whose dispatch date and delivery date differ. The environment gains that starting state and keeps it.

## What is hard

The realism of a simulator is the hardest part to get right. This method makes weak fidelity visible. It does not make good fidelity cheap. On physical systems, expect most of the verification effort to go into the things that cannot be simulated at all.
