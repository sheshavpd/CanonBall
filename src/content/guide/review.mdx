## What arrives

A milestone that is built and verified, and the Verification Record computed for it.

Two reviews can happen here. The first always does.

## The agent review

The **reviewer** is an agent with its own account. It can read everything and write nothing but its review. It did not build the code and did not write the checks.

It reviews every milestone and every piece of unplanned work, and asks five questions.

1. **Does every behavior trace to a clause?** Code that does something no clause asked for is a finding.
2. **Does the actual change in behavior match the predicted one?** The verification environment runs the same recorded requests against the old build and the new one, and the orchestrator lists every response that differs. The reviewer explains each difference as a bug, a gap in the canon, or a wrong prediction.
3. **Are the design choices written down?** A choice the agents made silently cannot be revisited.
4. **Is the evidence honest?** Each check encodes its example, each has a recorded failure, and nothing in `verify/` was weakened.
5. **How large is the blast radius?** What can break if this is wrong, for whom, and can it be undone?

## What it found

The predicted change was: small refunds move from review to automatic approval, and nothing else changes.

The actual change has a second line. When the gateway loses a reply, the new build retries the payout five times where the old one retried three. The builder had edited the payout code, which the design said would not be touched. No clause asks for it, and retries are exactly where a refund gets paid twice.

The reviewer sends it back and the builder removes it. If someone wants five retries, that is a request, and it goes to [Collect](../collect/).

## When a person reviews too

A person reviews when the policy lists the change as critical, or when the reviewer rates its blast radius as large. The team's policy lists these cases.

| A person reviews when the change | Why |
|---|---|
| touches a constraint or an action that cannot be undone | Someone must answer for it |
| alters a clause about safety or money | The cost of being wrong is high |
| changes code that touches the outside world | It is the code evidence covers least |
| makes the status of any clause worse | Something was traded away |
| behaves differently from what was predicted, and the difference is kept | Nobody agreed to it |
| has a blast radius the reviewer rates as large | Many customers or clauses are exposed if it is wrong |

This person-review is the **release gate**. When no case applies, the milestone goes to release on the agent review alone.

M2 changes which refunds are paid without a person looking. That is money, so the refunds owner reviews it.

## What the person reads

The refunds owner reads three things, and none of them is the diff.

- **The Verification Record.** DEC-031 is accepted: three checks, each seen to fail. No other clause got worse.
- **Predicted against actual behavior.** After the fix, they match.
- **The case for INV-004**, since money is involved: why a refund still cannot be paid twice when the gateway loses a reply.

The owner signs off, and the sign-off is recorded on the milestone. What the gate records is that a named person took responsibility for the remaining risk.

The one kind of code a person is asked to read is code that touches the outside world. After the fix, M2 changes none.

## Why both

The reviewer reads everything, every time. It can also share the builder's misreading of a clause, because both are models reading the same words.

A person reads little and reads slowly, brings judgment, and can be held to account. So the agent covers everything, and people's attention goes where the consequences are.

Review has no level of automation to turn up or down. What a team adjusts over time is the policy's list of what counts as critical: a cautious team starts with a longer list and shortens it on track record. [Handing over decisions](../delegation/) describes how.

## What leaves

A reviewed milestone, signed off by its owner. It is ready for [Release](../release/).
