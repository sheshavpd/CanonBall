## Pick the system

Choose one system you already run. Good candidates share three traits.

| Trait | Why |
|---|---|
| **Logic-heavy** | It has rules that matter: money, eligibility, state transitions. |
| **Long-lived** | You will be changing it for years. |
| **Small enough to hold** | One service with one database is ideal. |

Do not start with a prototype or a user-interface project. The method fits them poorly.

## The week

<Figure id="week" />

### Days 1 and 2: write down what is true

Write the vocabulary. Then write ten clauses describing what the system does today: a few promises, a few invariants, one constraint, one assumption with a one-line treatment. Give each one examples, both satisfying and violating.

Put them in a first change folder and release it. That first release writes `spec/`. From this point, only a release changes it.

Expect this to raise questions about words. Answer them in the vocabulary.

### Day 2: say what counts as evidence

Write two short policy files.

| File | Says |
|---|---|
| **Acceptance** | Which clauses are critical. To begin: a clause is accepted when every example has a check, every check passed at this commit, and every violating example has a recorded failure. |
| **Gates** | Three lines. A person accepts every release. Who reviews critical cases. Who approves when an owner is away. |

Add the traceability check to continuous integration. It is a script that reads front matter and fails the build when something traces to no clause.

### Days 3 to 5: build one environment

This is the largest piece of the week.

1. **One command to start, one to destroy.** The service, its real local database, and a fake for each outside dependency.
2. **A short declaration,** ending with what the environment cannot show.
3. **Four verbs** as a small library: set up state, drive the system, make a dependency misbehave, observe.
4. **One check per example,** each naming the example it encodes.
5. **A recorded failure for every violating example.** Break the build with a small patch, run the check, keep the failing output.
6. **A hook in the test runner** that writes one line of evidence per check per run.

> **A prerequisite.** The service must be startable with its outside dependencies pointed elsewhere. If it is not, creating that seam comes first, and the week slips by however long it takes.

### Day 5: compute the Verification Record

Write a script that joins three things: the list of examples, the assurance cases, and the lines of evidence. It prints one row per clause.

```text
INV-003 | unsupported | checks 3/3 | seen to fail 1/2 | missing: violates/2
```

Publish that table as a page. Do not commit it.

### Throughout: separate the identities

Create three agent identities with write access limited by path: one drafts clauses and plans, one writes `src/`, one writes `verify/`. Keep a handful of scenarios, written by people, in a repository none of the three can read.

## What to do now and what to leave

| Do this now | Leave for later |
|---|---|
| Ten clauses with examples and IDs. A vocabulary. A purpose page. | Sentence conventions, a values ranking, precedents as files |
| A policy with two files | The other policy files. Conservative defaults apply meanwhile. |
| One-line cases for ordinary clauses. Hand-reviewed cases for critical ones. | Generated cases, a verification plan, fidelity claims |
| The traceability check, as a script | Tracing changes in behavior to clauses |
| The Verification Record as one generated table | The five statuses, signed evidence |
| One verification environment | The rest of the environment machinery |
| Three agent identities | Separate elicitor and planner agents |
| A roadmap page and a board in the tracker you already use | A purpose-built orchestrator |

Everything in the right-hand column stays in the method. You adopt each item when a pilot shows you need it.

## The first surprise

Some clause will stay unsupported because the environment cannot yet check one of its examples. A typical case is a race between two requests, which needs a way to hold a timing gap open that you have not built.

Leave it unsupported and name the missing example. A check that cannot really fail would turn the row green and make the Record worthless.

## What comes next

Run changes through it. Twenty ordinary rule changes, each starting as a change proposal, will teach you more than any amount of setup. Include a refactoring, a bug fix and one failed release.

Measure four things from the first day.

| Measure | What it tells you |
|---|---|
| Minutes of a person's time per change, by gate | Whether review actually shrank |
| Escaped defects | What the checks and environments cannot see |
| How often evidence went stale | Whether the assurance cases are maintainable |
| Where the effort went | Whether verification really is most of the work |

Those numbers decide which [levels of automation](../delegation/) move, and which of the deferred pieces you need.
