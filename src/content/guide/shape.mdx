## What arrives

A one-page proposal arrives: refunds under $100 are approved automatically. It reads clearly and hides two decisions.

## A word nobody defined

Before drafting a clause, the elicitor checks the proposal's nouns against `vocabulary.md` and finds one undefined: whether $100 means the order total or the refund. It asks the product manager, with the two readings side by side, and the answer goes into the vocabulary.

```text
Refund amount   The money returned by one refund. Not the order total.
```

An agent that guessed would have built one of the two readings, and nobody would have known which until a customer complained.

## An example exposes a choice

One of the elicitor's examples for the proposed decision has no obvious answer.

> Given an order of $150, when the customer asks for $60 back, and later for another $60, then what?

Each refund is under $100 and together they are not, and the proposal does not say which counts.

The elicitor recommends counting everything refunded on the order, and cites the first of the team's [tenets](../tenets/): a person's review over speed, when money moves. The product manager agrees, and the decision is recorded as a clause with the examples that fix its meaning.

```markdown
id: DEC-031
kind: decision
traces: [REQ-012]
---
A refund is approved automatically while the total
refunded on the order stays under $100.

Why: tenet 1.

Satisfies:
- A $40 refund, nothing refunded before: approved without review.
- Two $60 refunds on one order: the second goes to review.
Violates:
- A $250 refund approved without review.
```

The risk team's request is now an example that a check will enforce.

## How it will be built

Who leads the design is each team's choice; this team's architect keeps the architecture and leaves detailed design to agents.

The architect makes one call: the new rule belongs in the **decision logic**, the part of the code that decides and touches nothing outside, and the payout code is not changed. The planner agent writes the rest of the design, with a **predicted change in behavior**:

> A refund moves from review to automatic approval while the total refunded on the order stays under $100. Nothing else changes.

At Review, the orchestrator compares this prediction with what actually changed.

## How it will be proven

The **evidence plan** is written now, before the code, for the reason scientists register a hypothesis before an experiment: a test written after the code can be shaped to fit it.

The verification lead and the verifier agent decide what the test must cover. The existing environment, VE-002, cannot yet set up an order that has already been partly refunded, so they add that starting state. It can already make its fake gateway lose a reply after paying, and the plan requires the automatic path to run against that failure, because a careless retry there would pay twice.

## The agreement gate

A **gate** is a point where a person must act before work moves on, and this one closes the station.

| Who | Approves |
|---|---|
| Product manager | The three examples for DEC-031 |
| Constraint owner | That ENV-003, the payout limit, is untouched |
| Verification lead | The evidence plan, including how the assurance case for INV-004 covers the automatic path |

People approve examples here, since no code exists yet.
