## The name

**Canon** is the set of clauses a system is held to. A **CanonBall** is what you get when you fix three things together at the moment of a release:

1. the canon as it stands,
2. the build that keeps it,
3. the Record that shows the build keeps it.

Draw them as concentric circles, with the canon at the center, and you have the mark at the top of this page. The method takes its name from the artifact because every iteration of the work ends in one.

## The question it answers

Hand someone a conventional release and they can run it. To find out what it promises, they read the documentation and hope it is current. To find out whether it keeps those promises, they read the code or trust the team.

A CanonBall answers both without anyone reading code.

> What does this system promise, and how do you know?

Different people ask that question at different times. A customer deciding whether to depend on you asks it. So does an auditor, and so does the engineer who inherits the system two years later.

## What is inside

```text
CanonBall 13
  canon    spec/canon at this release
  build    commit 3f9c
  record   4 accepted, 0 unsupported
  notes    + DEC-031 Refunds under $100 are approved automatically
```

Four properties separate it from a tagged commit.

| Property | What it means |
|---|---|
| **Release notes are clause changes** | A new CanonBall means these promises changed. Versioning follows behavior, so weakening a clause others rely on is a breaking release, however small the code change. |
| **The evidence can be re-checked** | A proof ships with the inputs to its checker, a simulation with its random seeds, a check result with the content hash of the code it ran against. A status nobody else can reproduce is only a claim. |
| **Assumptions travel with it** | It states what it assumes about where it runs, the way a package states its dependencies, and includes the monitors that notice when an assumption stops holding. |
| **Scope stays visible** | Each clause appears with its status, the conditions under which the evidence holds, and anything still open. A bare "passed" is never shown. |

## Only clauses that are kept

A CanonBall contains the clauses the system keeps at that release. A clause that has been agreed and is still being built is not in it. The same rule governs [`spec/`](../repository/): the canon describes the system as it is.

## For one team

For a single team building for itself, none of the packaging matters. A repository with a `spec/canon/` folder, a rule about who may release, and a Record that is computed on every push is already a private CanonBall.

Signing, registries and exchange formats become useful on the day you hand the artifact to someone who did not watch it being built. Until then they are overhead.

## Across teams

When one system depends on another, it pins the CanonBall version it relies on. When the provider publishes a new one, the dependent re-runs the checks that rest on it. The chapter on [larger systems](../composition/) describes how evidence composes this way without anyone reading another team's code.

## Is it a framework?

There is nothing to install and no library to import, so "framework" overstates it. CanonBall is a method: a set of written artifacts, a repository layout, a division of work between people and agents, and a rule for what counts as a release. The tooling is small and mostly scripts, and you could write your own.
