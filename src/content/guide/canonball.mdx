## The name

**Canon** is the set of clauses a system is held to. A **CanonBall** is what you get when you fix three things together at the moment of a [release](../release/):

1. the canon as it stands,
2. the build that keeps it,
3. the Verification Record that shows the build keeps it.

The CanonBall mark draws one turn of that work: its three arcs are the canon, the build and the Record, and the ball leaving the loop is the release. The method takes its name from the artifact because every iteration of the work ends in one.

## The question it answers

Someone who is handed a release as a build alone can run it. To find out what it promises, they read the documentation and hope it is current, and to find out whether it keeps those promises, they read the code or trust the team.

A CanonBall answers both questions without anyone reading code.

> What does this system promise, and how do you know?

Different people ask that question at different times: a customer deciding whether to depend on you, an auditor, and the engineer who inherits the system two years later.

## What is inside

```text
CanonBall 13
  canon    spec/canon at this release
  build    commit 3f9c
  record   4 accepted, 1 accepted with stated risk, 0 unsupported
  notes    + DEC-031 A refund is approved automatically while the
             total refunded on the order stays under $100
```

The record line counts five clauses: the four the refunds service kept at CanonBall 12, and DEC-031.

A CanonBall differs from a tagged commit in these ways.

| Property | What it means |
|---|---|
| **Release notes are clause changes** | A new CanonBall means these promises changed. Versioning follows behavior, so weakening a clause others rely on is a breaking release, however small the code change. |
| **The evidence can be re-checked** | A proof ships with the inputs to its checker, a simulation with its random seeds, a check result with the content hash of the code it ran against. A status nobody else can reproduce is only a claim. |
| **Assumptions travel with it** | It states what it assumes about where it runs, the way a package states its dependencies, and includes the monitors that notice when an assumption stops holding. |
| **Scope stays visible** | Each clause appears with its status, the conditions under which the evidence holds, and anything still open. A bare "passed" is never shown. |

A CanonBall holds only clauses that have been released with evidence. A clause still being built is not in it. Accepted means supported by the evidence so far, not proven.

## For one team

For a single team building for itself, none of the packaging matters. A repository with a `spec/canon/` folder, a release rule, and a Record that a program, the orchestrator, computes on every push is already a private CanonBall.

Signing, registries and exchange formats become useful on the day you hand the artifact to someone who did not watch it being built. [Larger systems](../composition/) covers what happens when another team depends on yours.

## Is it a framework?

There is nothing to install and no library to import, so "framework" overstates it. CanonBall is a method: a set of written artifacts, a repository layout, a division of work between people and agents, and a rule for what counts as a release. The tooling is small and mostly scripts, and you could write your own.
