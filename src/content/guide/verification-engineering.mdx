## The inversion

When people wrote the code, the product took most of the effort and testing came second. With agents writing the code, the balance turns over. Producing the change is quick. The engineering goes into building a place where you can find out whether the change is right.

**Verification engineering** is the name for that work. It has three parts.

1. Decide, for each clause, what would count as evidence.
2. Build [environments](../environments/) in which that evidence can be produced.
3. Keep the evidence trustworthy as the system changes.

An environment is designed, it has known limits, and it can be wrong. That is why this is engineering and not housekeeping.

## What a test suite does not tell you

A conventional suite answers "did the tests pass?" Four questions go unanswered.

| Question | Where CanonBall records the answer |
|---|---|
| Which promise is each test evidence for? | Every check names the example it encodes. |
| Could this test ever fail? | Every check keeps a run in which it did. |
| What did the test assume about the outside world? | Assumptions are listed in the assurance case. |
| Which promises have no test at all? | The Verification Record shows them as unsupported. |

## The assurance case: one per clause

An **assurance case**, or *case* for short, is the bridge between a clause and its evidence. The term and the idea come from safety engineering.

<Figure id="case" />

A case has four elements.

| Element | What it is |
|---|---|
| **Parts** | The clause, split into pieces that can each be checked. |
| **Assumptions** | Whatever depends on the outside world, named. |
| **A method and an environment** | One of each, for every part. |
| **An argument** | Why those parts, taken together, are enough. |

The argument is where real gaps hide. A verified move gate and a fast sensor do not add up to "no robot moves near a person". Braking distance and sensor blind spots have to be accounted for as well. Writing the argument down is how someone notices that they were left out.

## The weakest dependency decides the method

For each part, ask one question.

> What must be true outside the decision logic for this claim to hold?

The answer places the part at a **level**, and the level tells you the method.

| Level | The claim depends on | Method | For software alone |
|---|---|---|---|
| 0 | Pure logic | Model checking, proof | Decision logic with no side effects |
| 1 | Concrete code | Property-based tests | Code run against fakes |
| 2 | Components interacting over time | Simulation, scripted scenarios | Real processes and a local database |
| 3 | Real devices, drivers, latency | Tests on real hardware | Real infrastructure, a staging system |
| 4 | Physics, materials, people | Measurement, field data | Production traffic |

Readers who know the test pyramid will see a family resemblance. The pyramid sorts tests by size. These levels sort claims by what they depend on. A level says nothing about confidence: a narrow proof about an abstract controller can leave a larger practical gap than a well-designed physical test.

<Figure id="levels" />

Two consequences follow.

**Control falls as realism rises.** In a level 1 environment you can freeze time and hold a race condition open. On real infrastructure you cannot. Timing bugs are therefore best caught low, and only observed high.

**A team's name for a test is not its level.** "Unit tests" are level 1 if they run real code. Place each part by what it depends on.

## Tiers: how much rigor

A full case for every clause would cost too much. Safety standards scale rigor to criticality, and so does CanonBall.

| Tier | Which clauses | The case | Review |
|---|---|---|---|
| 0 | Most. Logic with no side effects | One part, generated | None |
| 1 | A few parts | A short argument | None |
| 2 | Safety, money, irreversible actions | A full argument, assumptions with treatments | A person |

Most clauses are tier 0. A person reads only the tier 2 arguments.

## The procedure for one clause

1. **Split** the clause into logic, assumptions and measured outcomes.
2. **Argue** why those parts establish the clause as deployed.
3. **Place** each part by its weakest dependency and choose the method.
4. **Treat** each assumption: how it is watched, how fast a failure shows, and what happens then.
5. **Decide** whether the evidence is enough, against the policy.
6. **Move the boundary.** If a part will not verify because the logic lives in the wrong place, move the logic. If it depends on the world, make that an assumption and give it a treatment.

Step 6 has a trap. Moving logic to where it can be checked is progress. Relabeling a hard problem as an assumption is not. The Record keeps the two apart by showing every assumption as an assumption.

## Cases go stale on their own

Every case lists the code its clause depends on, with a content hash of that code. When the code changes, the clause shows as *unknown* until the case is checked again. The chapter on [evidence](../evidence/) describes the mechanism.

## What a proof does not give you

A proof shows that the logic satisfies a property for every input. Four things remain, and each has its own cover.

| A proof does not show | What covers it |
|---|---|
| That the property is the right one | Examples |
| That the world behaves as assumed | Treatments |
| That the parts are enough | The argument |
| That the code matches the model that was proved | Checks against recorded behavior |

In the Record, "proven" always appears with its property, its model, its bounds, and its assumptions.

## Who does this work

The verifier agent builds the environments and checks. People decide what counts as evidence, review the arguments for critical clauses, and review any change that would weaken an environment.
