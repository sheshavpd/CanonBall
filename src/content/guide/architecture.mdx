## Agents need structure more than people do

A person can hold a tangled system in their head, because they were there when it became tangled. An agent has only the files in front of it, so the quality of its work depends on how much of the system it can reason about from them.

Good architecture has always made software easier to change. For a team that works with agents it also decides how cheaply anyone can find out whether a change is right, and what the running system did.

## A recommendation

The rest of the method works on any codebase. The layout recommended here is the one that makes evidence and observability cheapest, and a team should adopt it where it fits and leave it where it does not.

## Separate the code that decides from the code that acts

<Figure id="core-shell" />

Most code decides and acts at once. A function reads the database, checks a rule, calls the payment gateway, and writes a row, so testing the rule requires a database and a gateway. The remedy is to move the rule into a function of its own.

```python
# Decides. No database, no network, no clock.
def decide_refund(order, refunded_cents, amount_cents, today):
    if (today - order.delivered_on).days > 30:
        return Reject("outside the refund window")
    if refunded_cents + amount_cents < 100_00:
        return Approve(payout=amount_cents)
    return SendToReview()
```

```python
# Acts. Gathers the inputs, asks for a decision, carries it out.
def handle_refund_request(request):
    order = orders.load(request.order_id)
    decision = decide_refund(
        order, refunds.total_for(order.id), request.amount_cents, clock.today()
    )
    if isinstance(decision, Approve):
        gateway.pay_out(order.id, decision.payout)
    ...
```

The first function contains every rule about who gets a refund and touches nothing, and the second contains no rules and touches everything. Milestone M2 of the refunds service depends on this split: the architect decides at [Shape](../shape/) that the rule for small refunds, DEC-031, goes into the first function and that the code that pays out is left alone.

## Two terms

**Decision logic** is code that, given explicit inputs, returns what should happen. It reads no clock, generates no random numbers, and performs no input or output. The time, a sensor reading, the output of a model: each is passed in as data.

An **adapter** is the one place where a particular side effect happens. Until something passes through an adapter, nothing has happened.

## Established names

The pattern is well established under several names, and a team should use whichever it already has.

| Name | From |
|---|---|
| Functional core, imperative shell | Gary Bernhardt |
| Ports and adapters, or hexagonal architecture | Alistair Cockburn |
| Pure functions and effects at the edges | Functional programming generally |
| Deciders | Event-sourced systems |

The CanonBall specification calls the two halves the *pure core* and its *doors*.

## Why it makes evidence cheap

| Property of decision logic | What you gain |
|---|---|
| No side effects | Thousands of generated inputs can be tested in seconds. |
| Explicit state and inputs | A model checker can explore every reachable state. |
| Deterministic | Any run can be replayed exactly from its recorded inputs. |
| Small and separate | The list of code that can break a clause is short and easy to name. |

The last row has the largest effect. Every [assurance case](../verification-engineering/) lists the code its clause depends on. If the rules about refunds live in one function, that list has one entry. If they are spread across handlers, queries and jobs, the list is long, it changes often, and the evidence goes stale constantly.

Adapters help in a different way. Each one is a narrow point through which an effect must pass, which makes it the natural place to enforce a [constraint](../primitives/#constraint), add an extra check, or require a person's approval before something irreversible happens.

## Why it makes observability cheap

Agents build, verify and operate by looking inside the system, and the same split keeps that affordable. Decision logic receives everything it uses as an argument, so nothing it relied on is hidden. Each decision can also name the clause it applied.

```python
    if (today - order.delivered_on).days > 30:
        return Reject("outside the refund window", clause="REQ-012")
    if refunded_cents + amount_cents < 100_00:
        return Approve(payout=amount_cents, clause="DEC-031")
```

The handler already holds the inputs and now holds the clause, so it can write one log line per decision with the clause, the inputs and the outcome, while the decision logic itself still performs no output. A line of this kind is what the on-call agent reads in incident INC-007 to see which clause refused a refund and which dates the decision was given, as [Operate](../operate/) describes.

In code that decides and acts at once, the inputs are spread across queries and calls, and every handler has to assemble that line by hand. The chapter on [observability](../observability/) covers what a system emits and the tools agents use to read it.

## What people still control

Who leads the architecture is a team's choice. An architect may write it, or agents may write it and revise it. The chapter on [handing over decisions](../delegation/) covers how a team sets that. Wherever it is set, people keep the following levers on the design.

| Lever | What it gives a person |
|---|---|
| **The interface** | What consumers depend on is a promise, and changing it needs approval. |
| **The constraints** | They have their own owner. |
| **How the product is divided** | Capabilities are split by whom they serve. This is decided early and sets how much work can run in parallel. |
| **The edges** | A small, fixed menu of deployment choices. The policy lists adapter code as critical, so a person [reviews](../review/) every change to it. |
| **Anything they choose** | Any design choice can be promoted to a [decision](../primitives/#decision) in the canon. |

## Where it does not fit

- **Interface-heavy products.** Most of the value is in layout and interaction, which have no decision logic to extract.
- **Prototypes.** The structure costs more than a throwaway is worth.
- **Hot numeric code.** Passing state in and out explicitly can cost performance the product needs.

In these cases the rest of the method still applies, and the evidence sits at a higher [verification level](../verification-engineering/#the-weakest-dependency-decides-the-method), where it is slower and less complete.

## Starting on an existing system

An existing system does not have to be restructured all at once. Start with the code behind its two or three most important invariants: extract the decision into a function with no side effects, leave the surrounding handler as the adapter, and write the checks against the function. Repeat when the next clause needs it.
