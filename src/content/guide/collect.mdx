## What arrives

Three requests reach the refunds team in the same week.

```text
roadmap/notes/
  support   small refunds wait two days in review
  finance   most review time goes to refunds under $100
  risk      split refunds must not slip past review
```

A **request** is anything someone asks of the system before it has been shaped. The elicitor agent files each one as it arrives.

## Why not build each one

An agent could build the first request in an afternoon, and that speed is the risk. The support request would have shipped before the risk request arrived, with nobody having decided what a split refund is.

Gathering requests first buys three things.

- **Decisions are made once.** All three cards turn on one question: which refunds may skip review? Answered once, it covers all three.
- **Agents get a whole.** A builder that sees the promise, the decision and the invariant together builds one coherent thing. A builder that sees one ticket builds that ticket.
- **A release means something.** A person can accept a milestone by reading what it promises. Nobody can read forty tickets.

People's attention is the scarce resource, and a milestone spends it once.

This is a batch of decisions. It is not a large batch of code: M2 is three requests, one decision and a few days of agent work.

## What makes a milestone

1. **It delivers something a customer can use, end to end.** It crosses every component the change needs. Work on one component is a task inside a milestone.
2. **It can be read in a minute.** If it cannot, it is split.
3. **It changes what the system promises.** It adds or alters a promise, a decision or a constraint. A milestone can be a single request, if that request does this.

A fourth request that week asks for refunds as store credit. It is a different promise with different decisions, so it becomes the next milestone, M3.

## The proposal

The elicitor drafts one page from conversations with the three people who asked.

```markdown
# M2: Faster small refunds

What changes: refunds under $100 are approved automatically.
Nothing else changes.

Gathers:   3 requests (support, finance, risk)
Why now:   the review queue is the slowest step for small refunds.
status:    draft
```

The page answers one question: what changes in the system? It says nothing about how. The orchestrator writes the `status` line, and nobody else does.

The product manager confirms that this is the right milestone and ranks it in `roadmap/index.md` by cost of delay. That ranking decides which page is shaped next.

## When work may skip the batch

Some work should not wait for a milestone. It is called **unplanned work**, and it rides the express belt. Three questions sort it.

| Question | If yes | Examples |
|---|---|---|
| Does it add or change what someone is promised? | It waits for a milestone. | Raising the $100 limit. Refunds as store credit. |
| Does it only restore or pin down an existing promise? | Express belt. A person approves the new example. | An incident repair. A bug fix. |
| Does it change no clause at all? | Express belt. Nothing to approve. | A refactoring. A dependency upgrade. |

Size is not the test. Raising the limit is one line of code, and it waits for a milestone because it changes a decision.

Express work skips the wait for a batch. It is still verified, still reviewed by an agent, and still released by the same rule. Each piece gets a folder under `roadmap/unplanned/` with the same shape as a milestone, only smaller. [Operate](../operate/) follows one.

## Several milestones at once

Two milestones that touch different clauses can be on the belt together and are released in whichever order they finish. Two that touch the same clause are one milestone, and the elicitor merges their pages.

## What leaves

A folder, `roadmap/M2-faster-small-refunds/`, holding one page that the product manager has confirmed. Next it is [shaped](../shape/).
