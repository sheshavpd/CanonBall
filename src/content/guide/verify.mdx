## What arrives

Code for the milestone arrives, with the evidence plan agreed at Shape.

Writing the rule took the builder an afternoon. Showing that it holds, in a way people can trust, is expected to be the larger job, called [verification engineering](../verification-engineering/).

## The environment is a product

The refunds service is tested in a **verification environment** named VE-002: the service itself, a real local database, and a fake payment gateway, started and destroyed by one command. The verification lead and the verifier agent designed it, and they keep a page that describes it.

```text
id: VE-002
name: payments-sandbox
boundary: the refunds service, at this commit
world: real local store; a fake payment gateway
control: seeded; one command up, one command down

## What it cannot show
Real gateway timing. Whether the real gateway honors
request keys. Production request shapes.
```

The last section matters as much as the rest, because evidence counts only within what the environment can show.

For this milestone the verifier extends the environment, as planned, to set up an order that has already been partly refunded.

The verification lead need not write the environment, but must be able to say in a sentence how each clause is checked: "the split-refund rule is tested by making two requests against a real store and reading what the fake gateway paid." If no person can say that, a green result means nothing to anyone. [Verification environments](../environments/) covers how one is designed.

## One check per example

Each approved example becomes one check, and the check names the example it encodes.

```python
@example_of("DEC-031#satisfies/2", "Two $60 refunds on one order")
def test_second_small_refund_goes_to_review(world):
    order = world.rig.order(amount_cents=15000).result
    world.act.api.refund(order, amount_cents=6000)
    second = world.act.api.refund(order, amount_cents=6000).result
    assert second.state == "in_review"
    paid = world.observe.gateway.payouts(order=order).result
    assert len(paid) == 1
```

An example with no check is visible, and so is a check with no example.

A second check runs the automatic path against a failure the fake gateway can simulate, in which the gateway pays and the reply is lost. The retry must find the original payout and pay nothing more, which covers INV-004 on the new path.

## Fail first

A check may be asserting something that is always true, and nobody can tell until it has been seen to fail. The verifier therefore breaks the code on purpose, in a scratch copy. This is an **injected fault**: one small patch, here making the limit apply to each refund instead of to the order's total. The check must fail against it.

```text
verify/faults/limit-per-refund.patch     applied to a scratch copy
test_second_small_refund_goes_to_review  FAILED   kept in verify/checks/red/
```

The failing run is kept. Only then is the check run against the real build, and only then does its pass count. [Evidence](../evidence/) covers the rule in full.

## What the builder cannot touch

Each agent role is a separate account, and the repository rejects a commit outside that role's paths. The builder can run everything in `verify/` and change none of it.

People also write a few held-out scenarios that neither agent can read. A run reports only pass or fail, and runs are rationed, so the scenarios are hard to tune against.

## When a check fails on the real build

The milestone goes back to [Build](../build/) without involving a person, because the clause is clear and the code is wrong. The verifier reads the trace and the decision log and reports what happened along with the failure.

## What leaves

The station produces one line of evidence for every run of every check. From these lines the orchestrator computes the Verification Record: the status of every clause with this milestone applied. The milestone and its Record go to [Review](../review/).
