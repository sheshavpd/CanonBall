## Status is computed

In CanonBall, nobody declares a clause, a task or a release to be done. The **orchestrator**, the program that computes every state and carries out a release, works it out from what exists.

The **Verification Record** is the computed status of every clause. The orchestrator reads the assurance cases and the results of the checks, applies rules that people own, and publishes the outcome. No agent and no person can write a status into the Record, because it is not a file in the repository.

The reviewer agent reads the Record for every change. A person at the release gate reads it as well when the policy lists the change as critical or the reviewer rates its blast radius as large, as the chapter on [review](../review/) describes. Whether a task is finished, and whether a change is ready to [release](../release/), are computed in the same way.

## A check must fail before its pass counts

Test-driven development has a rule: watch the test fail before making it pass. A check that has never failed proves nothing, because it may assert something that is always true, it may be testing the fake, or it may not be running at all. CanonBall makes the rule a condition of acceptance.

<FailFirst />

Every check is run once against a build that has been broken on purpose. The break is an **injected fault**, a small patch to the code that is kept in `verify/faults/`. The failing run is kept beside the check as a **recorded failure**, and the check's pass counts only when that file exists.

```text
INV-004   unsupported   checks 3/3   seen to fail 2/3
INV-004   accepted      checks 3/3   seen to fail 3/3
```

Both lines show three passing checks, and only the second supports the clause. Mutation testing applies the same idea across a whole suite, whereas here it is applied to each check in turn.

## A line of evidence

Each run of each check writes one line.

```json
{"clause": "INV-004", "part": "a",
 "check": "verify/checks/test_inv_004.py::test_concurrent_copies_pay_once",
 "example": "INV-004#violates/1",
 "environment": "VE-002", "commit": "3f9c",
 "assumptions": [], "seed": 4411,
 "state": "passed",
 "recorded_failure": "verify/checks/red/test_concurrent_copies_pay_once.json"}
```

The line records which clause the run is evidence for, which example the check encodes, what code it ran against, in which environment, with which random seed, and what happened. That is enough for someone else to run it again, and evidence that cannot be reproduced is treated as a claim.

## Five statuses

<Figure id="rollup" />

The status of a clause is a decision, not a confidence score.

| Status | Meaning |
|---|---|
| **Accepted** | Every part has evidence that is in range and current. |
| **Accepted, with stated risk** | Accepted, with an assumption that is watched but not proven. |
| **Unsupported** | Some part lacks evidence, or a check failed. The Record says which. |
| **Pending** | Agreed, and waiting on another team to provide something. |
| **Unknown** | Not yet assessed, or the code the case rests on has changed. |

The Record can be trusted because it never averages and never omits. The weakest link is named: a clause with three strong parts and one missing part is unsupported, and the Record names the missing part. A gap is never hidden: a part that ran and saw nothing is shown as unsupported and is not left out.

For the refunds service at CanonBall 13, the Record's summary reads "4 accepted, 1 accepted with stated risk, 0 unsupported".

## Evidence that does not count

A passing run is not always evidence. Runs of the following kinds are marked and set aside.

| Marked as | Why it does not count |
|---|---|
| **Stale** | The code, the environment, or a fake has changed since the run. |
| **Out of range** | The run was outside what the environment was validated for. |
| **Self-produced** | The builder ran it, and nothing independent checked it. |
| **Discounted** | The environment has stopped catching injected faults. |
| **Never reached** | The check was about a race, and the race never happened. |

## How staleness works

Everything that evidence depends on carries a content hash: the code a clause relies on, the environment's declaration, each fake. When any of them changes, the hash changes, and the evidence that relied on it is stale until the check runs again. Because one mechanism serves every kind of dependency, evidence never silently outlives the thing it was about.

The same mechanism keeps runs affordable. A change re-runs only the checks for clauses whose code it touched, in the way a build system skips what has not changed.

## When a check fails

Every failing check is classified before anyone acts on it.

| Label | Meaning | Next step |
|---|---|---|
| **Bug** | The build is wrong. | Fix the code. |
| **Gap** | A clause is missing. | Propose one. |
| **Noise** | The environment misbehaved. | Fix the environment. |
| **Ambiguity** | The clause has two readings. | Ask a person. |

The label decides what happens next, and it is recorded. Retrying a failed check until it passes is not allowed, because it weakens the evidence without telling anyone.

## Assumptions and monitors

A clause that depends on the outside world cannot be fully proven. In the refunds canon, ASM-011 says that the payment gateway pays at most once per request key, and no check in VE-002 can establish that about the real gateway. Such an assumption gets a **treatment**, which states:

- how it is observed in production;
- how long a failure would take to show;
- what the system does when it fails;
- what is accepted when a failure could not be detected at all.

A monitor that raises an alarm is a treatment. It does not show that the clause holds, and at best it supports "accepted, with stated risk".

When a monitor fires, an incident opens, and the repair comes back as a small piece of unplanned work with a new example and often a new invariant. Operating the system improves the canon in this way, and the chapter on [operating](../operate/) follows one incident from the first report to the release.

## The policy

The rules that turn evidence into status live in `spec/canon/policy/`. People write them, and no agent can.

The policy says what counts as evidence for each tier, what counts as an independent check, which kinds of oracle are trusted, and which changes are critical enough that a person must review them before release. A change that would lower the bar is reviewed explicitly.
