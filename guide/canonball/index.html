What a CanonBall is

A CanonBall is the canon bound, at one moment, to the build that keeps it and the Verification Record that shows it.

In this chapter

  • A CanonBall is three things fixed together: the canon, the build, and the Verification Record.
  • Every release produces one, and progress is a sequence of them.
  • It answers "what does this system promise, and how do you know?" without anyone reading code.

The name

Canon is the set of clauses a system is held to. A CanonBall is what results from fixing three things together at the moment of a release:

  1. the canon as it stands,
  2. the build that keeps it,
  3. the Verification Record that shows the build keeps it.

The CanonBall mark draws one turn of that work: its three arcs are the canon, the build and the Record, and the ball leaving the loop is the release. The method takes its name from the artifact because every iteration of the work ends in one.

In the figure, CanonBall 13 carries a milestone and CanonBall 14 carries the repair of an incident. Both were released by the same rule.

The question it answers

A person who receives a release as a build alone can run it. To learn what it promises, they read the documentation and hope it is current; to learn whether it keeps those promises, they read the code or trust the team. A CanonBall answers both questions without anyone reading code.

What does this system promise, and how do you know?

Different people ask that question at different times: a customer deciding whether to depend on the system, an auditor, and the engineer who inherits the system two years later.

What is inside

## CanonBall 13

- released: 2026-03-10
- from: roadmap/archive/M2-faster-small-refunds
- build: 8ca1c6a
- record: 4 accepted, 1 accepted, with stated risk
- adds or changes: DEC-031 Auto-approve under $100

This is its entry in CANONBALLS.md, written by tools/canonball release. The canon is spec/canon at the commit that records the entry. The record line counts five clauses: the four the refunds service kept at CanonBall 12, and DEC-031.

A CanonBall differs from a tagged commit in the following ways.

Property What it means
Release notes are clause changes A new CanonBall means these promises changed. Versioning follows behavior, so weakening a clause others rely on is a breaking release, however small the code change.
The evidence can be re-checked A proof ships with the inputs to its checker, a simulation with its random seeds, a check result with the content hash of the code it ran against. A status nobody else can reproduce is only a claim.
Assumptions travel with it It states what it assumes about where it runs, the way a package states its dependencies, and includes the monitors that notice when an assumption stops holding.
Scope stays visible Each clause appears with its status, the conditions under which the evidence holds, and anything still open. A bare “passed” is never shown.

A CanonBall holds only clauses that have been released with evidence, so a clause still being built is not in it, and “accepted” means supported by the evidence so far rather than proven.

For one team

A single team building for itself has no need of the packaging. A repository with a spec/canon/ folder, a release rule, and a Record that the orchestrator computes on every push is already a private CanonBall.

Signing, registries and exchange formats become useful when the artifact is handed to someone who did not watch it being built. Larger systems covers the case in which another team depends on yours.

Is it a framework?

There is nothing to install and no library to import, so “framework” overstates it. CanonBall is a method: a set of written artifacts, a repository layout, a division of work between people and agents, and a rule for what counts as a release. The tooling is small, mostly scripts, and a team could write its own.
