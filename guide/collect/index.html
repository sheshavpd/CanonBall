Collect: requests gather into a milestone

Requests are gathered into a milestone before anyone builds, so that their promises can be decided together.

In this chapter

  • Each request is a card, and related cards gather into one milestone, described by a one-page proposal.
  • A milestone delivers something a customer can use, reads in a minute, and changes what the system promises.
  • Work that restores a promise, or changes none, takes the express belt: it skips the batch and none of the stations.

What arrives

Three requests reach the refunds team in the same week.

roadmap/notes/
  support-small-refunds-wait.md     Small refunds wait two days in review
  finance-review-time-under-100.md  Most review time goes to refunds under $100
  risk-split-refunds.md             Split refunds must not slip past review

A request is anything someone asks of the system before it has been shaped. The elicitor agent files each one as it arrives, as a short file that says who asked and what for.

Why not build each one

An agent could build the first request in an afternoon. Had it done so, the support request would have shipped before the risk request arrived, and nobody would have decided what a split refund is. Gathering the requests first prevents this.

  • Decisions are made once. All three cards turn on one question, which refunds may skip review, and a single answer covers all three.
  • Agents get a whole. A builder that sees the promise, the decision and the invariant together builds one coherent change, whereas one given a single ticket builds only that ticket.
  • A release means something. A person can accept a milestone by reading what it promises, which is impractical for forty separate tickets.

A milestone spends people’s attention, the scarce resource, once for the whole batch. The batch is of decisions, and the code stays small: M2 is three requests, one decision and a few days of agent work.

What makes a milestone

  1. It delivers something a customer can use, end to end. It crosses every component the change needs. Work on one component is a task inside a milestone.
  2. It can be read in a minute. Otherwise it is split.
  3. It changes what the system promises. It adds or alters a promise, a decision or a constraint. A milestone can be a single request, if that request does this.

A fourth request that week, store-credit.md, asks for refunds as store credit. It is a different promise with different decisions, so it becomes the next milestone, M3.

The proposal

The elicitor drafts one page from conversations with the three people who asked.

# M2: Faster small refunds

What changes: refunds under $100 are approved automatically.
Nothing else changes.

Gathers:   3 requests: roadmap/notes/support-small-refunds-wait.md, finance-review-time-under-100.md,
           risk-split-refunds.md
Why now:   the review queue is the slowest step for small refunds. Support handles complaints about the
           wait every day, and reviewers spend most of their time on refunds they almost never turn down.
Adds:      to be settled at Shape

status: draft   (written by canonball)

The page states what changes in the system and leaves how to later stations. Only the orchestrator writes the status line, when tools/canonball status runs.

The product manager confirms the milestone and ranks it in roadmap/index.md by cost of delay, and that ranking decides which page is shaped next.

When work may skip the batch

Some work should not wait for a milestone. It is called unplanned work, and it travels on the express belt. What it does to the canon decides which belt it takes.

Question If yes Examples
Does it add or change what someone is promised? It waits for a milestone. Raising the $100 limit. Refunds as store credit.
Does it only restore or pin down an existing promise? Express belt. A person approves the new example. An incident repair. A bug fix.
Does it change no clause at all? Express belt. Nothing to approve. A refactoring. A dependency upgrade.

Size is not the test: raising the limit is one line of code, and it waits for a milestone because it changes a decision.

Unplanned work skips the wait for a batch but is still verified, reviewed by an agent, and released by the same rule. Each piece gets a folder under roadmap/unplanned/ shaped like a milestone’s, only smaller. Operate follows one.

Several milestones at once

Two milestones that touch different clauses can be on the belt together and are released in whichever order they finish. Two that touch the same clause are one milestone, and the elicitor merges their pages.

What leaves

The station’s output is a folder, roadmap/M2-faster-small-refunds/, holding one page that the product manager has confirmed. The milestone is then shaped.
