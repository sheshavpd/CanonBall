# When writing code is cheap

> An agent can write a change in minutes, but finding out what the change does takes as long as it ever did.

Key points:
- Producing a change is now cheap, and the scarce skill is knowing what a change does.
- A specification helps an agent build the right thing and says nothing about how well that thing was checked.
- On a system built by agents, verification is expected to take most of the engineering effort.

## A familiar afternoon

An agent opens a pull request that touches fourteen files, and the tests pass. You have twenty minutes before your next meeting, so you can either read the change properly and be late, or skim it and approve it on trust.

Both options get worse as agents get faster. If you read everything, the agent waits for you and its speed is wasted; if you stop reading, every change carries a risk that nobody has measured.

[Figure: Twelve changes, two ways to review them.]
Two panels. Left, "Review every change": twelve changes all go to a person, and the queue grows or the reading stops. Right, "Review the promises": an agent reviews all twelve; two are critical and go to a person as well; the other ten are checked by machines against promises already agreed.

## What changed

Producing a change used to cost enough effort that its author understood it, and code review gave a second reading to work that a person already understood. An agent now produces working code faster than a person can read it, so the scarce skill is answering two questions about a change:

- What does this change actually do?
- What does the system still promise after it?

Many codebases answer neither question well. Side effects are spread through the code, state is shared, and tests check whatever their author happened to think of. A green build reports that some tests passed, and says nothing about which promises were tested or how thoroughly.

## Why a specification is not enough

Giving the agent a written specification addresses half of the problem, because the agent then builds the right thing more often. Tools that track a specification stop short of the other half. They can report that a requirement has a test, but not what kind of test it is: a requirement covered by one example and a requirement covered by a proof look the same on a dashboard, and neither entry records what was assumed or left out.

## The idea CanonBall borrows

Safety engineering has used a tool for this for decades, on aircraft and medical devices. It is the **assurance case**: a written argument, backed by evidence, that a system meets a claim. An assurance case states what was checked, by which method, under which assumptions, and what is still open. Assurance cases are rare outside regulated industries mainly because they are expensive to write and to keep current by hand.

> **The bet.** Agents can bring the cost of an assurance case down to the cost of ordinary software. If the agents that write the code also maintain the argument for it, and independent machinery checks them, any system can carry an account of its own promises.

## Where the effort goes instead

If the bet holds, the distribution of effort is expected to change.

| | When people write the code | When agents write it |
|---|---|---|
| Most effort goes to | Writing the product | Showing that the product keeps its promises |
| People approve | Code, one change at a time | Promises and worked examples; critical changes at release |
| "Done" means | Merged, with a green build | Every promise has evidence, and the weakest one is named |
| An incident produces | A fix | A fix and a permanent example |

The work in the right-hand column is [verification engineering](../verification-engineering/agents.txt): building places where a promise can be shown to hold, and shown to fail when it should.

> **A claim to resist.** Current models can do most of this labor, and that alone does not make the result trustworthy. Trust comes from running the method on a real system and measuring what gets through.

The process that supports this work, from the first request to the running system, is set out in [How work moves](../workflow/agents.txt).
